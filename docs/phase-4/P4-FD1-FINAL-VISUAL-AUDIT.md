**Status: PASS — audit and design planning complete.** Reviewed 29–30 September 2026. This is not a pass for the current frontend's final visual quality. Implementation has not started.

## Major diagnosis

The product has better task structure than visual expression. Applicant progress, Student schedules, staff entity headers, separate filter/sort controls, and explicit sample-data boundaries are useful. The failure is that their visual grammar gives too many things similar weight: pale background, white rectangle, small gray explanation, blue action. The same grammar repeats from public content to technical reference pages.

At 1920px, the 100rem shell and 70rem operational cap leave substantial unused space while Technology identities wrap inside an unnecessarily narrow master/detail table. At 375px, generous repeated header gaps, disclosure cards, module introductions, and nested panels push actual work below the first screen. These are complementary problems: desktop needs useful width; mobile needs fewer layers of presentation.

Arial is not the sole cause. Replacing it while retaining the same surfaces, card frequency, header anatomy, and width caps would preserve most of the generic appearance. The final direction must change those rules together.

## What should disappear, and what should become stronger

Remove decorative yellow dots, routine card borders around disclosures, unnecessary nested panels, duplicate visual headline treatments, filled tab trays used as default decoration, and giant neutral gaps before the task. Remove the second seal on login when the shared masthead is present. Do not remove disclosure meaning, existing fields, status words, sample-document warnings, tabs, or actions.

Strengthen the original seal's masthead setting, campus photography, selected navigation, current task, entity identity, table structure, and section rules. Existing plain Student announcements, mobile Records rows, Applicant journey, Academic lead notice, and inline selected Technology detail should be models for restraint. Whitespace around a short read-only page is acceptable; it is a defect when it narrows real work or separates closely related controls.

## Old rules contributing to the result

The earlier design system solved inconsistency but over-constrained visual development: Arial-only typography, `#F8FAFC` canvas with white panels and `#E5E7EB` borders, a 70rem operational cap, 8px/12px universal geometry, and small accent usage. Its “compact” Demo Notice became a bordered card with independent width. Its 24/32px header spacing combines with feature margins into excessive mobile preambles. “Plain section” was permitted but not the default, so the card remained the easiest composition.

Not every weakness was required by the old lock: nested cards and generic SaaS appearance were already discouraged. Public history rules, Student plain lists, and Records mobile rows demonstrate that better hierarchy is possible within the architecture. The explicit supersession table in [P4-FINAL-VISUAL-LOCK.md](P4-FINAL-VISUAL-LOCK.md) replaces the limiting visual values and makes surface/composition choices enforceable. UX behavior and institution facts are not superseded.

## Evidence qualifications and next boundary

- Capture labels are not always visible-state descriptions. IDs 0400/0401/0434 are **inline** DCAT review regions below the first viewport, and 0249 is an inline document preview. Full-page inspection confirmed them; they must not be described as modal dialogs. ID 0384 shows the portal switcher on desktop; at mobile that desktop control is hidden, so its mobile capture is a collapsed-shell comparator, not proof of an open mobile switcher.
- The manifest reports no unresolved capture failures and records two recovered capture attempts. Source/hash and path checks were repeated; authentication, viewport dimensions, and gallery operation are attributed to the capture record, not newly tested here.
- The corpus has login and validation errors, but no general fetch-failure or loading-state captures. Those visual recipes are specified prospectively and require implementation evidence. No new backend state is authorized to manufacture them.
- Screenshots cannot prove focus trapping, keyboard operation, text zoom, screen-reader output, font loading, print pagination, reduced motion, or physical-device behavior. These remain FD2–FD4/M7 acceptance checks.
- This pass selects one final direction and a 35-state paired golden set. No source code, styles, fixtures, packages, routes, auth/access, database, or workflow was modified. **FD2 is not started.**
