## 2. Design direction and retained tokens

Keep Source Sans 3 for UI and Source Serif 4 only for public editorial headings. Keep the 4px spacing base, 44px minimum control target, 6px control / 8px panel-overlay / 4px badge radii, circular avatars, and current shell dimensions.

Use existing roles: blue `#0D13CD`, yellow `#FCDF00`, ink `#17233B`, canvas `#EDF0F4`, base `#FFFFFF`, inset `#E3E8EF`; retain existing secondary text, borders and semantic palettes. Public pages remain editorial; portals remain task-oriented. Expression comes from response, alignment and selective accents, not new content.

## 3. Motion system and interaction recipes

**Thesis:** an action visibly answers; context changes retain continuity; public admissions/history have a bounded authored sequence. No animation owns the availability of data, focus or controls.

| Token           | Value                        | Use                                                                     |
| --------------- | ---------------------------- | ----------------------------------------------------------------------- |
| Immediate       | 0ms                          | Focus ring, state/ARIA update, validation, escape/close, reduced motion |
| Press           | 80ms                         | Control surface compression, never click dispatch                       |
| Feedback        | 140ms                        | Hover color/border, link underline, input border                        |
| Continuity      | 180ms                        | Tabs, selected context detail, menu/dialog arrival                      |
| Drawer          | 220ms                        | Drawer entrance only                                                    |
| Public sequence | 320ms; total sequence ≤500ms | Admissions connector/history line; see §4                               |
| Feedback ease   | `cubic-bezier(.2,0,0,1)`     | Color/border/press release                                              |
| Arrival ease    | `cubic-bezier(.16,1,.3,1)`   | Entering overlay, selected marker, public detail                        |

Use explicit properties, never `transition: all`. Prefer existing CSS plus a tiny opt-in observer/helper if necessary; no motion dependency. No bounce, spring overshoot, parallax, cursor effects, looping shimmer, animated counters, spinning seals or global scroll smoothing. State updates happen on the original event with no artificial delay/debounce. Interrupted motion settles to the newest state; rapid input never queues animations.

### Pending, errors, and performance

Only actual existing asynchronous operations show pending state, with reserved control width and the existing label/disabled behavior. Do not introduce a minimum spinner time. Validation summary/field focus is immediate; never shake a form. Text confirmation remains after visual emphasis ends. No global `will-change`; decorative layers may use transform/opacity during their short active interval. Do not animate layout dimensions or retain a previous sensitive screen for a crossfade. Cancel observers/animations on teardown and when motion preference changes.

## 4. Public scroll and portal differences

Public Home's hero title, photo and both CTAs are visible from first paint. The ordered admissions section earns a connector reveal: on first intersection, draw only the decorative blue connector with a yellow leading segment over 320ms, with up to 36ms stagger across its five steps (≤464ms total). All numbered steps, descriptions and links are fully visible before/during it. This illustrates reading order, not the visitor's admission progress.

The existing history section on Home/About earns one line/keyline reveal over 320ms, with at most 8px movement on a noninteractive heading group. Dates and factual entries remain visible and still. Programs may emphasize its section keyline once in 180ms; do not animate four table rows independently. Admissions page reuses the admissions recipe. No reveal on login, account recovery/creation guidance, legal/disclaimer text, error pages or footer links.

Use progressive enhancement: default CSS is the complete final state. Observer activates only decoration, once per mounted section, at roughly 15% intersection. A section already visible on restoration, reached by fragment, or containing keyboard focus gets its final state immediately. Rapid scroll, failed scripts, disabled JS, printing and reduced motion expose everything; nothing waits for scroll. No blanket fade-up wrapper on every section.

Portals have **no scroll reveals** for task data, forms, results, notices or rosters. Their visible liveliness comes from the full interaction matrix, overlay arrivals and meaningful state feedback. A plain reading/reference page does not need motion on every paragraph.

## 7. Shared avatar + add-photo interaction

Extend existing `Avatar` / `IdentitySummary` and replace permanent `DemoProfilePhotoPicker` blocks with one reusable photo-action component. Use an 80px profile avatar, 32px shell/menu avatar, and the current small avatar for lists. On editable profile avatars only, place a 28px visible plus disk at bottom-right inside a **44×44px nonoverlapping button hit area**. Reserve enough surrounding space that it cannot cover the adjacent name/link. Accessible label: “Add demo photo” or “Change demo photo”; the plus is decorative and always visible.

Choose one shared native **dialog**, not separate desktop popover/mobile implementations. Title “Demo profile photo”; first visible text: “Shown only in this tab. Not uploaded or saved. Resets on reload or sign-out.” Follow with existing JPEG/PNG/WebP, up to 2 MB constraints, preview, Choose image, Use photo, Cancel, and conditional Remove photo. File input exists only inside the interaction; a labeled Choose image control invokes it. No permanent file-input strip on the page.

Flow: open dialog → choose image → validate type/size and decode → show staged preview → Use photo commits presentation state and closes → avatar/menu update immediately. Native chooser cancellation preserves current/staged selection; dialog Cancel/Escape discards staged changes. Remove photo restores initials immediately and announces “Demo photo removed”; no destructive confirmation for this reversible local action. Decode/type/size failure keeps prior image, shows associated inline error, and leaves retry/cancel available. Keep 2 MB validation behavior consistent at the boundary; fix contradictory “smaller than” versus “up to” wording if needed without raising the limit.

Retain object URL handling, revoke replaced/staged/discarded URLs and all URLs at reset. Do not revoke a committed URL merely because the dialog closes or a route unmounts while its state persists. No base64 storage, crop editor, remote URL field, camera permission, cloud upload or account-photo backend. Profile image is personal presentation, not an admissions document or requirement.

Dialog must have an accessible name, initial focus on Choose image, contained Tab order, Escape, reachable close/cancel and return focus to the originating plus. At 320px use viewport-minus-32px width, bounded dynamic-viewport height and internal scroll; keep actions reachable with the software keyboard. One dialog instance per editing interaction; no nested dialogs. Announce update/remove/errors once. Initials remain the complete fallback when image loading fails.

## 8. One shared Account Profile

**Route decision: reuse `/account`.** Preserve its existing `getCurrentAccessContext()` and unauthenticated redirect. This avoids nine pages, a new route family, a new API or an added authorization rule. Title becomes “Account profile”; the neutral institutional shell remains, with existing authorized portal destinations and sign-out. No fake current portal on this neutral route.

Server page passes a minimal presentation DTO to one shared client profile view: current `user.id`, `user.name`, `user.email`, `identity.status`, and existing membership/role labels and paths. Do not pass session identifiers/tokens, permission arrays, database models or a list of other users. `getApplicationSession` already rejects inactive accounts; show the actual returned state rather than inventing disabled-account access. Empty memberships render the existing honest no-access state. The frontend store is never an authorization source.

Page hierarchy: identity band (avatar, signed-in name, email, account status) → About/Bio → Portal memberships and roles → existing account/session explanation and safe destinations. At desktop use a ≤1216px composition with a ≤672px personal region and 320–352px membership rail where it fits; mobile follows that logical order. Name/email/status/memberships/roles are read-only. Keep one main heading, ordinary section rules and limited panel use; no cover photo, statistics, badges for every field or profile-completion percentage.

Campus/program/functional context is **omitted by default**: the current account DTO contains membership/role labels, not verified domain affiliations. Only render optional context if an already available, explicitly linked identity object supplies it; do not join new tables, copy another person's domain fixture or infer campus from role. Role labels themselves provide useful existing functional context. No birthday, address, phone, salary, private HR fields, official biography or fabricated account timestamps.

### Account entry

Desktop and mobile keep the clearly labeled Account trigger; a small account avatar may precede its label if it fits. In the open menu, make the existing identity block a single link to `/account` with an accessible name identifying the destination, and rename the repeated Account destination to **View profile**. No nested link around another interactive control. Preserve Sign out and the existing authorized portal-switch controls/locations; do not duplicate every portal choice into another competing menu. Mobile drawer's Account destination also reads View profile. On the Account page it is Current profile or `aria-current="page"`.

Keep existing disclosure semantics unless an actual accessible menu implementation is warranted; do not add `role="menu"` to ordinary links without its full keyboard model. Menu closes on destination activation; Escape closes and restores trigger focus. Long names/email wrap. Open overlays remain within viewport, above content, without covering their own close/return path. One Account interaction per shell, distinct from navigation.

## 9. Bio, identity separation and demo state

Account Bio is optional **frontend demo state**, initially empty. Empty text: “No demo bio added.” Edit bio exposes a labeled textarea with a 240-character limit and visible counter, “Apply demo bio” and Cancel. Treat it as plain text, never HTML/Markdown; preserve entered text on validation error, and do not prefill a fictional biography. Applying or clearing updates only the local view with “Demo bio updated in this tab”; no autosave claim. Empty applied value clears the bio. The limit is a presentation constraint, not school policy.

Use one client presentation-state provider mounted inside the existing root `<body>` around children, surviving client navigation between `/account` and `[portal]`. Keep root/page/layout Server Components and existing domain workflow providers in their current roles. Installed Next docs' client-provider pattern supports this plan; FD6 must reread relevant local guides before writing code.

The neutral provider holds only local photo/bio state. Existing guarded account/portal entry points pass the stable signed-in user ID through a small client binding; no root-level auth fetch or guard move. Gate reads synchronously by this ID so an old user's avatar is never rendered while an effect catches up. An identity change clears the previous account's state and object URLs. Anonymous pages display no stored identity/photo/bio. State survives ordinary in-app links and authorized portal switching within the current tab, but not a full document reload, new tab, browser restart or successful sign-out. A remount/navigation path that loses state must be fixed or truthfully disclosed before acceptance; never silently add browser storage to mask it.

Sign-out integration clears only presentation state while retaining the current sign-out call, redirect and refresh semantics. Clear state on identity mismatch/session loss; do not implement a new session timer. Back/Forward after sign-out must not reveal the prior custom image/bio. A full reload returns empty bio and initials. No cross-tab sync or remote persistence. Exact user copy: “Photo and bio are temporary in this tab. They reset on reload or sign-out.”

### Account identity is not a sample domain record

The current Student account and displayed Student fixture differ; Applicant draft fields can also diverge. Therefore:

- Account menu, shell account avatar and `/account` always share the **account** scope keyed by signed-in ID.
- Applicant/Student domain profiles retain their existing name, email, ID, school facts and separately labeled **sample profile photo** scope. Reuse the same avatar/dialog implementation. Keep their existing domain-provider photo lifetime unless explicitly adopting a proved identity mapping; do not move or reset any workflow state.
- Never copy bio into the Applicant/Student record, mutate a fixture, synchronize names, or assume a common person from a portal membership. Do not show the signed-in user's custom photo on a different sample person.
- Add a short distinction on domain profiles: “Sample school profile. Your sign-in identity is in Account profile,” linking to `/account`. Existing school contact fields remain on the domain page only.

This locks a safe, consistent model without a backend mapping project. Shared components do not require shared records. Future true account/domain photo unification needs an explicit existing stable relationship and separate approval if it requires data changes; it is not a blocker for this plan.

## 10. Mobile and reduced-motion contract

At 320/375px use one task column, 16px content gutters, no page overflow, full labels and ≥44px actionable targets. At 768px evaluate actual available space; no premature two-column form/rail. Preserve current drawer breakpoint. Tables may scroll only inside labeled comparison regions; mobile lists retain field labels. Long tabs use a bounded one-line scroll strip with a visible overflow cue and keyboard-current item kept in view, not shrinking text or wrapping into an accidental second tier.

Group title/context/disclosure tightly: 8px internal gaps, 16px to first task on mobile and 24px on desktop. Do not independently apply outer gaps to each child. Preserve essential caveats; remove duplicate title styling rather than deleting meaning. Profile photo helper text lives in the dialog; temporary-state explanation remains discoverable before selection. No sticky bottom bar or rail that obscures controls.

For `prefers-reduced-motion: reduce`: **all nonessential animation/transition duration 0ms; transforms removed; no stagger, scroll reveal, smooth scrolling, shared-element travel or crossfade**. Show final indicators, text, focus and selected states immediately. Static borders/fill/text, existing live announcements and disabled/pending labels carry feedback. This applies to every newly introduced helper and existing M7/public-menu animation, even if preference changes while an overlay is open. Print also uses final state. No animation may be needed to understand a result.
